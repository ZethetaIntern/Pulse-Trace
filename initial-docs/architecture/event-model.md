# Event Model

Project: PulseTrace

Version: 1.0

Status: Draft

---

# Purpose

This document defines the event model used throughout PulseTrace.

Events are the foundation of observability.

Every important state transition in the notification lifecycle generates an immutable event.

These events collectively provide a complete execution history that powers debugging, analytics, replay, monitoring, and auditing.

---

# Event Philosophy

Events represent historical facts.

An event records **what happened**, **when it happened**, and **why it happened**.

Events are:

- Immutable
- Append-only
- Chronological
- Traceable
- Independently queryable

Events are never updated or deleted.

---

# Why Events Exist

Instead of only storing the current notification status:

```
Status = DELIVERED
```

PulseTrace stores the complete journey.

```
NOTIFICATION_CREATED

↓

REQUEST_VALIDATED

↓

NOTIFICATION_STORED

↓

JOB_QUEUED

↓

WORKER_STARTED

↓

PREFERENCE_CHECKED

↓

TEMPLATE_RESOLVED

↓

TEMPLATE_RENDERED

↓

CHANNEL_SELECTED

↓

PROVIDER_INVOKED

↓

DELIVERY_SUCCEEDED
```

This makes every notification fully explainable.

# Event Lifecycle

Every notification execution generates an ordered sequence of events.

External Application

↓

Notification Created

↓

Validation

↓

Queue

↓

Worker

↓

Delivery Engine

↓

Provider

↓

Final Status

Each transition produces exactly one event.

# Event Structure

Every event contains:

```
Event

├── Event ID
├── Notification ID
├── Execution ID
├── Event Type
├── Previous Status
├── Current Status
├── Metadata
├── Timestamp
```

---

# Event Fields

## Event ID

Globally unique identifier.

Purpose

Uniquely identify every event.

---

## Notification ID

References the notification.

All events belonging to one notification share this value.

---

## Execution ID

Groups events belonging to a single execution.

Original notification

Execution ID A

Replay

Execution ID B

This allows multiple executions while preserving history.

---

## Event Type

Represents what occurred.

Example

JOB_QUEUED

---

## Previous Status

Notification status before transition.

---

## Current Status

Notification status after transition.

---

## Metadata

Flexible JSON object.

May contain:

Provider

Failure reason

Latency

Retry count

Worker ID

Any contextual information.

---

## Timestamp

Exact time the event occurred.

Used for:

Timeline

Analytics

Monitoring

Replay

Stored

↓

↓

↓

Preference Checked

↓

Template Rendered

↓

---

# Failure Flow

```
Provider Invoked

↓

Delivery Failed

↓

Retry Scheduled

↓

Retry Started

↓

Provider Invoked

↓

Delivered

OR

DLQ_MOVED
```

Every failure remains visible.

---

# Replay Flow

```
Original Notification

↓

Replay Requested

↓

New Execution

↓

Processing Begins

↓

New Timeline
```

Replay never modifies previous events.

---

# Event Ordering

Events are ordered using:

1. Timestamp
2. Event ID (tie-breaker)

Ordering must always remain deterministic.

---

# Event Immutability

Events cannot be:

Updated

Deleted

Modified

Historical accuracy must be preserved.

---

# Event Generation Rules

Generate an event when:

Status changes

Worker starts

Worker completes

Provider called

Retry scheduled

Replay starts

Replay completes

Any unexpected failure occurs

Do NOT generate events for internal implementation details.

---

# Event Metadata

Metadata is stored as JSON.

Example

```json
{
  "provider": "Resend",
  "latencyMs": 248,
  "workerId": "worker-1",
  "retryCount": 1
}
```

Metadata varies by event type.

---

# Timeline Generation

Timeline is generated by:

```
SELECT *

FROM NotificationEvents

WHERE notificationId = ?

ORDER BY occurredAt ASC;
```

Timeline is always event-driven.

---

# Replay Relationship

Every replay receives:

New Execution ID

Same Notification ID

Original history remains untouched.

Replay events become part of the same notification history but belong to a different execution.

---

# Event Naming Convention

Events use:

UPPER_SNAKE_CASE

Examples

NOTIFICATION_CREATED

JOB_QUEUED

DELIVERY_FAILED

REPLAY_COMPLETED

---

# Logging Relationship

Events are NOT logs.

Logs help developers.

Events describe business history.

Both may exist.

Logs may be deleted.

Events should remain permanently.

---

# Analytics Relationship

Analytics reads events.

Examples

Success Rate

Delivery Time

Failure Rate

Retry Count

Most analytics should be derived from events instead of notification records.

---

# Monitoring Relationship

Monitoring uses recent events.

Example

Worker failures

Queue backlog

Provider failures

Recent delivery latency

---

# Dashboard Relationship

The dashboard consumes events to display:

Timeline

Replay History

Status History

Delivery History

Processing Duration

---

# Database Mapping

Events are stored in:

NotificationEvents

Every row represents one event.

Events never overwrite previous rows.

The Event Model is successful when:

Every notification has a complete execution history.

Failures are fully explainable.

Replay preserves historical accuracy.

Analytics can be generated from events.

Timeline queries are efficient.

Developers rarely need external logs to understand notification behavior.
